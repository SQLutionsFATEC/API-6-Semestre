
## DoD (Definition of Done)

Aprovação do cliente (rastreável pelo Jira) de forma inequívoca. O cliente deve confirmar as características de uma certa user story, desde o seu fluxo, estrutura, prioridade e comportamento.

Entendimento da equipe; a equipe deve entender o contexto e a intenção da User Story e ser capaz de transformá-la em trabalho viável. Determinável pelo Planning Poker, Sprint Daily e protótipo visual navegável.

Estar dentro do prazo de Sprint Planning. User Stories não podem ser inclusas fora do período de Sprint Planning.

Deve estar documentada no Confluence ou no repositório principal da aplicação.

Além dos critérios de aceite diretos, toda User Story deve idealmente ter as seguintes características:

Independente: Uma User Story deve ser independente de outra User Story ou funcionalidade do sistema. 

Negociável: Os detalhes da User Story devem ser criados em conjunto com o cliente e os desenvolvedores de forma flexível.

Agrega valor: Uma funcionalidade deve possuir valor para o cliente ou os usuários do sistema.

Estimável: Os desenvolvedores devem ser capazes de criar uma estimativa para a implementação da história.

Pequena: As histórias devem ser pequenas o suficiente para serem criadas rapidamente. No nosso caso, idealmente em um dia de aula ou menos.

Testável: Deve ser possível, para cada User Story, criar testes para a sua funcionalidade.

## DoR (Definition of Ready)

Adere aos critérios de aceitação do cliente

Adere aos padrões de desenvolvimento (DevOps):

Funcionalidade passou em todos os processos de revisão de código

Funcionalidade está presente na branch principal do repositório

Funcionalidade deve ser rastreável a partir de cada commit até a User Story.
